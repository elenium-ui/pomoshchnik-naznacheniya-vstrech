# Промпт для нейросети на разработку mini-app по этапам

## Назначение документа

Этот документ нужен для практической поэтапной разработки `mini-app` через нейросеть.

Он должен помочь:
- не смешивать `mini-app` и существующий бот;
- не перепрыгивать через этапы;
- заставлять нейросеть не только писать код, но и проверять его;
- обновлять чек-листы в [Этапы разработки для mini-app.md](</Users/elenarazumova/Desktop/Vibe-project/Согласование встреч Google календарь/Этапы разработки для mini-app.md>);
- минимизировать количество действий, которые должен вручную делать пользователь.

## 2. Старт нового чата

Если начинается новый чат, не нужно сразу просить нейросеть писать код.

Сначала дайте ей контекст и заставьте подтвердить, что она поняла проект.

### Стартовый промпт для нового чата

```text
Работаем над проектом «Запись на встречу».

Сейчас мы начинаем отдельную ветку разработки для Telegram Mini App.

Я прикладываю документы Mini App:
1. Техническое задание для mini-app
2. Архитектура проекта для mini-app
3. Стек технологий для mini-app
4. Этапы разработки для mini-app
5. Структура экранов и переходов для mini-app
6. Контент и тексты для mini-app
7. UI-концепция и дизайн-система для mini-app

Дополнительно я могу приложить документы текущего бота как контекст существующего проекта.

Сначала ничего не реализуй и не пиши код.

Твоя задача на этом сообщении:
1. Изучить документы.
2. Коротко пересказать, как ты понял проект Mini App.
3. Коротко назвать согласованную архитектуру и стек.
4. Сказать, что первым этапом идет Этап 0.
5. Перечислить, что нужно подготовить до старта Этапа 0.
6. Явно подтвердить, что ты не будешь смешивать Mini App с уже существующим ботом.
7. Не писать код, пока я отдельно не попрошу.
```

### Как понять, что нейросеть ответила правильно

Хороший ответ должен:
- упомянуть, что `Mini App` строится поверх текущего backend ядра;
- назвать стек примерно как `React + TypeScript + Vite` и `FastAPI + текущий Python backend`;
- явно сказать, что первым идет `Этап 0`;
- не перейти к написанию кода.

## 3. Общий базовый промпт для любого этапа

Ниже базовый промпт, который можно использовать почти для всех этапов.

```text
Ты senior full-stack разработчик и архитектор.

Мы разрабатываем Telegram Mini App для проекта «Запись на встречу».

Важно:
- Mini App не должен ломать существующий Telegram-бот.
- Mini App должен использовать текущее backend-ядро, а не дублировать бизнес-логику.
- Работать нужно строго по документам проекта.

Документы проекта:
1. Техническое задание для mini-app
2. Архитектура проекта для mini-app
3. Стек технологий для mini-app
4. Этапы разработки для mini-app
5. Структура экранов и переходов для mini-app
6. Контент и тексты для mini-app
7. UI-концепция и дизайн-система для mini-app

Дополнительный контекст:
- существующий бот уже реализован;
- при необходимости можно изучать документы бота как справку, но сейчас реализуется именно Mini App.

Обязательные правила:
1. Сначала изучи текущий этап и связанные документы.
2. Не перепрыгивай на следующие этапы без необходимости.
3. Не смешивай Mini App с bot-only файлами.
4. Используй согласованный стек:
- frontend: React, TypeScript, Vite, React Router, TanStack Query, React Hook Form, Zod, SCSS Modules
- backend: Python 3.12, FastAPI, Uvicorn, Pydantic v2, SQLAlchemy 2, Alembic
- переиспользуй текущее backend-ядро проекта
5. Обязательно добавляй логи на каждом важном действии.
6. После реализации сам выполни максимум проверок:
- unit tests
- integration tests
- smoke checks
- просмотр логов
- проверка, что бот не сломан
7. Если какая-то проверка невозможна без меня, дай очень простую пошаговую инструкцию без сложных терминов.
8. Если видишь риск, конфликт с ТЗ или архитектурную проблему, напиши об этом сразу.
9. После завершения этапа обязательно открой файл «Этапы разработки для mini-app.md» и обнови:
- общий статус этапа
- чек-лист текущего этапа
10. Нельзя ставить `[x]`, если пункт не проверен.
11. Если есть сомнения, ставь `[!]` и честно объясняй, что осталось.

Формат ответа после выполнения этапа:
1. Что реализовано.
2. Какие файлы созданы или изменены.
3. Как устроено решение.
4. Какие проверки выполнены автоматически.
5. Какие логи посмотреть.
6. Что проверить мне вручную пошагово.
7. Какие риски или ограничения остались.
8. Обновленный чек-лист текущего этапа.
```

В ответе дай:
1. Что проверено.
2. Какие проблемы найдены.

## 8. Шаблон запроса на ручную проверку для новичка

Если нейросеть просит вас что-то проверить, но объясняет слишком сложно, можно отправить:

```text
Перепиши инструкцию ручной проверки очень простым языком, как для новичка.

Формат:
1. Что открыть.
2. Куда нажать.
3. Что должно появиться.
4. Что делать, если появилась ошибка.

Без сложных технических терминов.
```

## 9. Что нейросеть должна помнить всегда

- Mini App и бот не должны конфликтовать.
- Существующая бизнес-логика не переписывается без необходимости.
- Frontend не должен сам решать бизнес-правила.
- Все важные действия логируются.
- Все критичные права проверяются на backend.
- Чек-лист этапа нужно обновлять не в ответе “словами”, а в самом файле этапов.

## 10. Рекомендуемый порядок работы

1. Новый чат: отправить стартовый промпт.
2. Дождаться подтверждения понимания.
3. Дать промпт на `Этап 0`.
4. После завершения этапа проверить чек-лист в файле.
5. Только потом запускать следующий этап.

Главное правило:
- не пытаться в одном сообщении заставить нейросеть одновременно изучить все документы, перепроектировать всё, написать весь код и провести всю приемку.
