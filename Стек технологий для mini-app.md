# Стек технологий для mini-app

## Назначение документа

Этот документ фиксирует рекомендуемый стек технологий именно для `Telegram Mini App` части проекта `Запись на встречу`.

Важно:
- документ относится только к `mini-app`;
- он не отменяет текущий стек бота;
- он описывает, какие технологии использовать при дальнейшей реализации и почему.

## 1. Принцип выбора стека

Стек должен быть:
- надежным;
- понятным для поэтапной реализации через нейросеть;
- достаточно современным;
- без лишней инфраструктурной сложности;
- совместимым с текущим Python backend;
- удобным для мобильного премиального UI;
- безопасным для Telegram Web App.

## 2. Итоговый рекомендуемый стек

## 2.1. Frontend

- `React`
- `TypeScript`
- `Vite`
- `React Router`
- `TanStack Query`
- `React Hook Form`
- `Zod`
- `SCSS Modules` + `CSS variables`
- нативный `Telegram WebApp API` через тонкий локальный wrapper
- `dayjs`

## 2.2. Backend и API

- `Python 3.12`
- `FastAPI`
- `Uvicorn`
- `Pydantic v2`
- `SQLAlchemy 2`
- `Alembic`
- существующий `aiogram 3`
- существующие application/domain services проекта
- существующая интеграция `Google Calendar API`

## 2.3. Инфраструктура и деплой

- `Docker`
- `docker-compose`
- существующий VPS
- reverse proxy через текущий инфраструктурный контур
- отдельный frontend-container для Mini App
- отдельный API runtime
- отдельный jobs runtime

## 2.4. Тестирование и качество

- `pytest`
- `pytest-asyncio`
- `httpx` для API-тестов
- frontend smoke/e2e проверки
- стандартный `logging`

## 3. Почему именно этот frontend-стек

## 3.1. React

Подходит лучше всего, потому что:
- хорошо справляется со сложными интерфейсами и состояниями;
- удобен для раздельных клиентского и админского режимов;
- хорошо подходит для SPA внутри Telegram;
- дает достаточно гибкости для premium mobile UI;
- легко масштабируется по экранам, формам и карточкам.

## 3.2. TypeScript

Нужен, потому что:
- снижает количество ошибок в формах, API и состояниях;
- помогает нейросети писать более аккуратный код;
- особенно полезен при большом количестве экранов, ролей и статусов.

## 3.3. Vite

Рекомендуется, потому что:
- быстро запускается локально;
- удобен для разработки SPA;
- хорошо работает с React и TypeScript;
- не тянет за собой лишней тяжелой архитектуры.

## 3.4. React Router

Нужен для:
- экранов клиента;
- экранов админа;
- переходов между карточками, формами и настройками;
- управляемой навигации внутри одного приложения.

## 3.5. TanStack Query

Нужен для server-state:
- получение заявок;
- получение слотов;
- обновление статусов;
- повторная загрузка данных после действий;
- кэширование и обновление экранов без ручной путаницы.

Он особенно полезен, потому что в Mini App будет много:
- списков;
- карточек;
- фильтров;
- экранов с повторной синхронизацией с backend.

## 3.6. React Hook Form + Zod

Это хорошая связка для:
- пошаговой записи;
- черновиков;
- редактирования контактов;
- валидации полей.

Почему лучше так:
- меньше ручного шаблонного кода;
- понятнее логика формы;
- валидация остается читаемой.

## 3.7. SCSS Modules + CSS variables

Это рекомендуемый подход для дизайна проекта.

Почему не стоит сразу уходить в тяжелую UI-библиотеку:
- у проекта важен свой визуальный стиль;
- нужен premium, а не шаблонный внешний вид;
- слишком агрессивный utility-first подход может сделать интерфейс менее цельным.

Почему это хороший выбор:
- удобно задавать дизайн-токены;
- удобно поддерживать фирменную палитру;
- можно аккуратно контролировать скругления, тени, плотность и адаптивность;
- проще не превратить интерфейс в “конструктор из готовых блоков”.

## 3.8. Нативный Telegram WebApp API

Для Telegram-функций рекомендуется использовать:
- нативный `window.Telegram.WebApp`;
- собственный тонкий adapter/wrapper в проекте.

Почему так:
- меньше зависимости от сторонних abstraction-библиотек;
- критичные вещи вроде `initData`, `MainButton`, `BackButton`, viewport и haptic будут контролироваться напрямую;
- проще дебажить и логировать.

## 4. Почему именно этот backend-стек

## 4.1. Python 3.12

Уже используется в проекте и остается правильным выбором:
- совместим с текущим кодом;
- не требует новой платформы;
- удобен для расширения существующей архитектуры.

## 4.2. FastAPI

Это рекомендуемый web/API слой для Mini App.

Почему именно он:
- хорошо подходит для HTTP API;
- естественно ложится в существующий Python-контур;
- удобно работать со схемами, валидацией и зависимостями;
- легко тестируется;
- хорошо подходит для отдельного runtime API.

Почему не стоит городить API прямо поверх случайных ad-hoc обработчиков:
- станет трудно тестировать;
- смешается логика транспорта и use case;
- вырастет риск поломки бота.

## 4.3. Uvicorn

Нужен как runtime ASGI-сервера для FastAPI:
- простой;
- зрелый;
- подходит для локального запуска и production.

## 4.4. Pydantic v2

Уже хорошо подходит проекту и должен использоваться для:
- схем API;
- сериализации ответов;
- валидации запросов;
- внутренней конфигурации.

## 4.5. SQLAlchemy 2 + Alembic

Сохраняются как основа доступа к данным.

Плюсы:
- не нужно плодить второй data-layer;
- легко сделать минимальные additive-миграции;
- удобно переиспользовать существующие модели и репозитории;
- сохраняется готовность к PostgreSQL.

## 4.6. Aiogram 3

Остается для бота:
- `/start`;
- уведомления;
- fallback;
- возможные кнопки открытия Mini App.

Менять bot-stack не нужно.

## 4.7. Google Calendar integration

Остается существующая интеграция.

Mini App не должен реализовывать отдельный новый календарный слой.

Его задача:
- вызывать уже существующее ядро;
- показывать корректный результат пользователю и администратору.

## 5. Дополнительные технологические решения

## 5.1. Состояние на frontend

Рекомендуется разделять:
- `server state` через `TanStack Query`;
- `form state` через `React Hook Form`;
- небольшой `UI/app state` через локальный context или легкий store.

Не рекомендуется:
- сразу вводить тяжелый глобальный state-manager без реальной необходимости.

## 5.2. Работа с датами

Рекомендуется использовать `dayjs`.

Причины:
- он достаточно легкий;
- удобен для UI;
- подходит для отображения дат, слотов и истории;
- помогает избегать хаоса в форматировании.

Ключевое правило:
- сервер остается источником правды по временным правилам;
- frontend не должен самостоятельно “придумывать” доступность.

## 5.3. Валидация Telegram `initData`

Рекомендуемый подход:
- валидировать `initData` на backend по официальному алгоритму;
- реализацию держать в своем security-слое;
- покрыть тестами;
- не доверять одной только frontend-инициализации.

## 5.4. Статическая отдача frontend

Рекомендуется:
- собирать frontend отдельно;
- отдавать собранный SPA отдельным контейнером;
- backend API держать отдельно.

Это проще для:
- деплоя;
- rollback;
- диагностики;
- независимого обновления frontend.

## 6. Что не рекомендуется использовать на старте

Чтобы не усложнять MVP, не рекомендуется сразу вводить:
- тяжелую микросервисную схему;
- отдельный message broker;
- Redis только “на всякий случай”;
- сложный SSR/Next.js слой без явной необходимости;
- тяжелую компонентную библиотеку, которая задавит дизайн;
- отдельный внешний auth-provider;
- отдельную вторую базу данных под Mini App.

## 8. Что считать согласованным по стеку

Стек можно считать согласованным, если:
- frontend остается SPA внутри Telegram;
- backend API делается в том же Python-проекте;
- bot-stack сохраняется;
- текущая база и миграции сохраняются;
- есть четкая граница между frontend, API и бизнес-ядром;
- стек не создает избыточной сложности для MVP.
